# PhoneAgent

Управление Android-телефоном с ПК через ADB. **Без нейросетей.**

Кидаешь видео → оно публикуется по расписанию. В остальное время телефон
сам разблокируется, листает ленту как живой человек и блокируется обратно.

## Как это работает

Элементы интерфейса ищутся **по тексту и resource-id в дереве экрана**, а не
по забитым координатам. Кнопка переехала после обновления приложения — скрипт
всё равно её найдёт. Так работает вся промышленная автоматизация тестирования
(Appium, UiAutomator), и это надёжнее и в десять раз быстрее vision-модели.

```
watch/ или Telegram  →  очередь (SQLite)  →  расписание с разбросом
                                                     │
                        ┌────────────────────────────┼────────────────┐
                        ▼                            ▼                ▼
                  разблокировка              публикация видео    живая сессия
                  (PIN из pin.txt)         (Intent + селекторы)   (лента, лайки)
```

## Установка

Нужен только Python 3.10+ и ADB. Внешних библиотек нет — `requirements.txt`
пустой намеренно, в нём расписано, что именно требуется помимо pip.

1. **ADB** уже лежит в `C:\Users\Admin\tools\platform-tools` и находится
   автоматически. Если переставишь — задай `ADB_PATH`.

2. **На телефоне:** Настройки → О телефоне → 7 раз тапнуть по «Номер сборки» →
   вернуться → Для разработчиков → включить **Отладка по USB**.
   Подключить кабелем, подтвердить отпечаток на экране телефона.

3. **PIN.** Если стоит блокировка — создай файл `pin.txt` рядом со скриптом
   и положи туда только цифры. Файл читается напрямую кодом разблокировки,
   в логи и скриншоты не попадает.

4. **Русский текст.** Штатный `adb shell input text` умеет только латиницу.
   Для кириллицы и эмодзи нужен ADBKeyboard (проект `senzhk/ADBKeyBoard`):
   ```
   python main.py install-keyboard
   ```

   На Xiaomi/MIUI установка с ПК запрещена оболочкой
   (`INSTALL_FAILED_USER_RESTRICTED`), и команда сама положит apk в
   `Download` на телефоне. Дальше **на телефоне**: Проводник → Download →
   `ADBKeyboard.apk` → Установить. Потом снова
   `python main.py install-keyboard` — установленный руками пакет система
   не включает сама, команда это доделает. Установить мало: пока клавиатура
   не **включена**, описания не наберутся.

5. Проверка:
   ```
   python main.py doctor
   ```

## Окно приложения

Всё то же самое, но мышкой:

```
python main.py ui
```

или двойным щелчком по **`Приложение.bat`** (он же пункт 6 в меню
`PhoneAgent.bat`).

Открывается обычное окно: статус телефона, зрения и клавиатуры вверху,
кнопки «смотреть ленту» и «опубликовать», состояние расписания, живой журнал
прогона, очередь с перетаскиванием видео, расписание и вкусы. Подключено
несколько телефонов — над выбором ленты появляется выбор телефона. Журнал в окне
тот же самый, что печатается в консоли, — строки идут в оба места сразу.

### Три ленты

Кнопка «Смотреть ленту» работает с **TikTok, YouTube Shorts и Instagram
Reels** — какая именно, выбирается кружками под кнопками, выбор
запоминается. У правил расписания приложение задаётся своё: можно смотреть
Shorts утром и TikTok вечером.

Список берётся из `recipes.json` («_feed_apps»), а не из кода: добавил туда
маршрут — лента сама появилась в окне и в расписании.

### Экран телефона прямо в окне

Рядом с журналом показывается сам экран телефона — видно, что агент делает,
без отдельного окна scrcpy. **По умолчанию выключен** флажком «экран
телефона»: кадр приходит в полном размере (720x1600, около мегабайта), а
панель шириной 232 пикселя, и разжимать такой PNG каждую секунду браузеру
дорого — окно начинает подтормаживать. Включённый обновляется раз в две
секунды в работе и раз в пять на простое. Выбор запоминается.

Показываются **те же кадры, которые снимает агент** (`livescreen.publish` из
`session._grab` и после каждого шага публикации). Второй источник заводить
нельзя: два `screenrecord` на одном телефоне мешают друг другу — соседние
команды adb проседали с 0,3 до 9 секунд, это уже ловили. Когда агент
простаивает, кадр снимается по запросу и не чаще раза в секунду, а страница
на простое просит его раз в три секунды: открытое окно не должно молотить
`screencap` круглые сутки.

Как это устроено: `webui.py` поднимает маленький сервер на стандартной
библиотеке, а страница (`webui.html`) открывается в **оконном режиме**
Chrome или Edge (`--app`) — без вкладок и адресной строки, отдельным окном в
панели задач. Если ни того, ни другого нет, страница откроется вкладкой в
браузере по умолчанию: выглядит хуже, работает так же. Зависимостей из PyPI
по-прежнему нет.

Порт по умолчанию 8765, занят — `python main.py ui --port 9000`.
`--no-window` поднимет только сервер, не открывая окно.

**Про безопасность.** Сервер слушает только `127.0.0.1`, проверяет имя хоста
и требует токен на каждое действие. Токен выдаётся самой странице при
загрузке и живёт до перезапуска. Без этого любая открытая в браузере
страница могла бы дёргать кнопки, которые двигают живой телефон.

**Одно действие за раз.** Телефон один: пока идёт сессия, кнопки публикации
заблокированы, и наоборот. Проверка и захват места держатся под одним замком —
претендентов четверо (кнопки, расписание, сторож очереди, бот), и без него двое
успевали проскочить одновременно.

**У расписания нет выключателя.** `Keeper` не работает, а сторожит: раз в
полминуты смотрит план и, если телефон свободен, ставит сессию в ту же
очередь, что и кнопки. Сам телефон он не занимает, поэтому выключать его
незачем — а раньше служба была длинным действием и блокировала кнопки, из-за
чего её и приходилось гасить руками.

**У каждого телефона своё хозяйство** (`devices.py`): папка
`devices/<серийник>/` с `plan.json`, `interests.json`, `watch/`, `queue/`,
кадрами, плюс колонка «чей телефон» в базе. Переключение — кружками на
главной. Наследство из общей папки достаётся только первому пространству:
второй телефон начинается с чистого листа.

### Собрать в .exe для другого компьютера

```
python build_exe.py
```

Нужен `pip install pyinstaller` — единственная зависимость во всём проекте, и
та только для сборки. На выходе `Desktop\PhoneAgent-exe\` и одноимённый
`.zip` (~31 МБ): распаковал на чужом ПК, двойной щелчок по `PhoneAgent.exe` —
откроется окно. Python на том конце не нужен.

Чем отличается от `build_transfer.py`: тот везёт исходники и требует Python,
этот — готовое приложение.

**Что где лежит и почему:**

| | где | почему |
|---|---|---|
| `webui.html` | внутри exe | часть программы, ищется через `sys._MEIPASS` |
| `recipes.json` | рядом с exe | маршруты правятся руками, когда соцсеть меняет интерфейс |
| `interests.json`, `plan.json` | рядом | настройки |
| `adb.exe`, `scrcpy` | `tools\` рядом | чужие программы, паковать их в свой exe незачем |
| `jobs.db`, `watch`, `logs` | появятся сами | нажитое не переносится |

**Главная тонкость сборки.** `config.BASE` в собранном виде считается от
`sys.executable`, а не от `__file__`: PyInstaller распаковывает код во
временную папку, которая стирается при выходе, и очередь с базой пропадали бы
после каждого закрытия. Проверено: рабочие папки создаются рядом с exe.

Запущенный без аргументов exe сразу открывает окно — печатать справку по
командам тому, кто щёлкнул по значку, бессмысленно. Все команды при этом
работают: `PhoneAgent.exe doctor`, `PhoneAgent.exe session tiktok` и так далее.

## Трансляция экрана

```
python main.py mirror                  # смотреть
python main.py mirror --control        # ещё и управлять мышью
python main.py mirror --record         # писать видео в logs/
python main.py post v.mp4 --watch      # видеть, что агент делает
python main.py serve --watch --record  # окно на время каждого действия
```

Работает на **scrcpy** (лежит в `C:\Users\Admin\tools\scrcpy-win64-v4.1`,
находится автоматически): настоящий H.264-поток, задержка 30–60 мс.

Управление мышью по умолчанию **выключено** — пока агент работает, случайный
клик по окну собьёт ему маршрут. Включается флагом `--control`, когда нужно
поправить что-то руками.

Если scrcpy почему-то недоступен, есть запасной просмотрщик на tkinter без
единой сторонней библиотеки: `python main.py mirror --simple`. Он медленный
(~2 кадра в секунду, каждый кадр — отдельный `screencap`), но работает всегда.

`--record` особенно полезен в сухом прогоне: агент отработал ночью, а утром
ты смотришь видео и понимаешь, где он промахнулся.

## Подключение к телефону: кабель

Основной и единственный нужный способ. Ничего настраивать не надо:

1. Воткнуть кабель.
2. Настройки → О телефоне → 7 тапов по «Номер сборки».
3. Для разработчиков → включить **Отладка по USB**.
4. Подтвердить отпечаток в диалоге на экране телефона.

Проверка: `python main.py doctor`.

Кабель быстрее сети в разы — это видно на съёмке кадра, которая делается на
каждый ролик: **~0,3 с по USB против 1-3 с по сети**. При разборе лентой
нейросетью это половина времени на ролик.

### Запасной путь по сети (выключен)

В `remote.py` живёт подключение по сети через туннель — ZeroTier, Tailscale
или свой WireGuard. Оно выключено флагом `REMOTE_ENABLED = False` в `config.py`
и ничего не делает, пока флаг не поднят.

Если понадобится: поставить `REMOTE_ENABLED = True`, поднять туннель на обоих
устройствах и один раз выполнить `python main.py remote pair <адрес>:<порт> <код>`
с кодом из «Беспроводной отладки» на телефоне. Дальше агент сам закрепит
постоянный порт 5555 и запомнит адрес; при воткнутом кабеле приоритет всё равно
у него.

Команды: `remote` (подключиться), `remote scan` (найти телефон в подсети
ZeroTier), `remote resume <порт>` (после перезагрузки телефона), `remote set
<адрес>` (задать вручную), `remote off` (закрыть доступ), `remote status`.

Два скрипта рядом нужны только для этого режима и в работе по кабелю не
участвуют: `lan_route.ps1` (чинит маршруты, если VPN на ПК забирает себе
локальную подсеть) и `exit_node.ps1` (делает ПК выходной нодой для телефона).

## Расписание сессий

Правил можно завести сколько угодно, каждое — «в такие-то дни недели, в
случайный момент такого-то окна, смотреть столько-то минут». Точное время
специально не задаётся: запуск ровно в 21:00:00 каждый вечер виден в логах
платформы за неделю, поэтому начало разыгрывается заново каждый день.

```
python main.py plan                                        # правила и что выпало на сегодня
python main.py plan --add 21:00-22:00 --minutes 30 --days пн-пт
python main.py plan --add 09:00-09:40 --minutes 10-20 --days "каждый день"
python main.py plan --add 23:00-01:00 --minutes 15 --days сб,вс
python main.py plan --off 2      # правило лежит, но не срабатывает
python main.py plan --remove 2
python main.py plan --edit        # править plan.json руками
```

Дни: `пн-пт`, `пн,ср,сб`, `будни`, `выходные`, `каждый день`. Латиница
(`mon-fri`, `weekend`, `daily`) понимается тоже — в cmd кириллица в
аргументах местами приезжает битой. Минуты — число или диапазон `20-40`.

Окно через полночь (`23:00-01:00`) считается **внутри одних суток**: сессия
встанет либо поздним вечером, либо ночью того же календарного дня. Так план
не теряет записи при смене даты.

Пока правил нет, сессии идут по `SESSION_TIMES` из `config.py`, как раньше.
Как только появилось хоть одно — расписание целиком ваше, случайные сессии
не подмешиваются, и **дневной лимит `MAX_SESSIONS_PER_DAY` на них не
действует**: он стоит против разгона случайного расписания, а расписанное
руками — это уже решение.

Работает всё это внутри `python main.py serve` — служба спит и просыпается
по плану. План перечитывается на смене суток, так что править `plan.json`
можно на ходу.

## Несколько телефонов сразу

Телефоны работают **одновременно и независимо**: пока один публикует видео,
другой смотрит ленту. У каждого своё расписание, своя очередь, свои вкусы и
своя строка в базе.

```
python main.py fleet            # поднять службы всех подключённых телефонов
python main.py fleet status     # кто сейчас работает
python main.py fleet stop       # попросить всех закончить
python main.py fleet --devices 74eed241 R58M12ABCDE    # только эти два
```

В окне для этого есть вкладка **«Флот»**: список телефонов, у каждого кнопка
запуска и остановки, и журнал его службы.

### Почему у каждого телефона свой процесс

Программа держит «с каким телефоном мы работаем» в глобальных переменных:
`config.SERIAL`, четыре пути в `config`, `plan.PATH`, `jobs.DEVICE`,
`adb._PREFERRED`. `devices.use()` их переставляет — потому окно и запрещало
менять телефон посреди работы.

Развести телефоны по потокам одного процесса значило бы перевести всё это на
контекстные переменные, до последней строки. Одна пропущенная — и видео
уходит в чужой аккаунт. Отдельный процесс решает это по построению: у него
свои глобальные переменные, свой `abort`, свой планировщик, а `adb -s` для
того и сделан, чтобы говорить с нужным телефоном.

Отсюда же следствие: **службы переживают закрытие окна**. У них своё
расписание, и им незачем зависеть от того, открыта ли страница. Новое окно
их подхватит и покажет как «запущена не из этого окна».

### Что всё-таки общее

| Ресурс | Как поделён |
|---|---|
| `jobs.db` | режим WAL: читатели и писатель не мешают друг другу |
| модель зрения | очередь на `VISION_MAX_PARALLEL` мест (`gate.py`) |
| сам телефон | замок: двое не поведут один аппарат |
| Telegram-бот | замок: `getUpdates` отдаёт второму читателю 409 |

**Про скорость.** Локальная модель одна, и она держит в памяти один
экземпляр — три телефона её не ускорят. При `VISION_MAX_PARALLEL = 1`
(по умолчанию для локального зрения) телефоны ходят к ней по очереди:
1.3 с на кадр остаются 1.3 с, но ждущий телефон ждёт. Считать в облаке
(`VISION_PROVIDER = api`) — там ограничение снимается само, запросы
обслуживаются параллельно по-настоящему.

**Про USB.** Кадры идут по кабелю, и телефоны делят шину. Три аппарата на
одном контроллере снимают экран медленнее, чем один.

### Остановка

Службу нельзя убивать: она может держать телефон посреди публикации, на
экране редактора. Поэтому остановка кооперативная — надзиратель кладёт
файл-просьбу, служба её замечает, обрывает текущее действие и выходит сама.
На это отводится 45 секунд, после чего процесс снимается принудительно.

## Зрение (опционально)

Визуальная модель. Нужна для двух вещей, и **ни одна из них не обязательна** —
без модели агент работает как раньше.

Считать модель может в двух местах, переключается на вкладке «Настройки»:

| Где | Что нужно | Чем хорошо |
|---|---|---|
| **В своей сети** — LM Studio на этом компьютере или на соседнем | видеокарта, 3 ГБ видеопамяти, запущенная программа | бесплатно, ничего не уходит наружу |
| **По API** — любой OpenAI-совместимый сервис | адрес, ключ и связь | модель крупнее и точнее, компьютер свободен |

Сервис не зашит в код: адрес, ключ и имя модели — три поля на вкладке
«Настройки». Подключается что угодно, лишь бы говорило по OpenAI-совместимому
протоколу и умело смотреть картинку: Qwen (DashScope), OpenRouter, DeepSeek,
сервер на арендованной видеокарте. Для частых адресов есть готовые пресеты.

Разговаривают оба по одному протоколу (OpenAI-совместимый `/chat/completions`),
поэтому в коде разница сведена к трём вещам — адрес, заголовок с ключом и имя
модели. Всё остальное в `vision.py` общее, и переключение ничего больше не
меняет.

**1. Разбор контента.** Во время сессии агент снимает по кадру с каждого
досмотренного видео в `frames/<сессия>/` и сразу отдаёт его модели — разбор
идёт **в фоновом потоке**, поэтому модель думает над кадром, пока агент уже
смотрит следующее видео, и тайминги не сбиваются. Результат ложится в таблицу
`content` (тема, категория, текст на экране, реклама, язык), а команда
`content` показывает сводку — во что лента утягивает аккаунт.

```
python main.py session tiktok --duration 300   # смотрит и разбирает на лету
python main.py content --days 7                # сводка
python main.py analyze                         # добрать неразобранное
```

Если модель не успевает за лентой (очередь на 4 кадра), кадр не теряется:
он остаётся на диске, и его подберёт `analyze`. Так же подбираются кадры
сессий, снятых при выключенном `VISION_REALTIME` или при упавшем LM Studio.

**0. Сначала — попасть в ленту.** Открытое приложение ещё не значит лента:
все три восстанавливают тот экран, где их закрыли, а YouTube и Instagram
вдобавок открываются на своей главной. Поймано живьём — сессия семь минут
свайпала страницу профиля и не разобрала ни одного ролика: свайп там ничего
не листает, а модель послушно описывала «пользователь просит отправить
фотографии».

Основной путь — **прямая ссылка** (`open_uri` в рецепте):
`instagram://reels_home` и `youtube.com/shorts` попадают в ленту сразу, мимо
любых вкладок. Для Instagram это единственный надёжный способ: его главная
показывает те же ролики, и по дереву «Дом» от «Reels» не отличить —
проверено сравнением, деревья почти одинаковые.

Запасной путь (и единственный для TikTok) — `session._ensure_feed`: жмёт
нижнюю вкладку, затем «Рекомендации» и **проверяет результат**. У TikTok
промаха два и лечатся они отдельно: не та нижняя вкладка и «Подписки», где у
свежего аккаунта пусто.

Как понять, что мы в ленте, зависит от приложения. У TikTok признак — дерево
интерфейса **не** снимается: uiautomator ждёт покоя, а там играет видео. У
Shorts дерево снимается и во время проигрывания, поэтому ему заданы
`feed_markers` — кнопки плеера («Приостановить видео»).

Две ловушки селекторов, обе споткнулись живьём:
- на каждую вкладку заводится **два** узла — кнопка с границами и текстовая
  подпись с `(0,0,0,0)`; тап по подписи уходит в никуда;
- `desc` сравнивается **по вхождению**: `{"desc": "Reels"}` совпал с
  «контейнер для панели видео Reels» посреди экрана, и агент открыл сторис.
  Поэтому у кнопок навигации стоит `"clickable": true`.

**2. Решения по теме.** Агент «взглядывает» на ролик 1,5-3 секунды — ровно
столько, сколько человеку нужно, чтобы понять, интересно ли ему. За это же
время модель называет тему, и по вкусам из `interests.json` агент либо
досматривает, либо листает дальше. В логе это видно построчно:

```
  смотрю 8.4с (решение 2.3с):    интересно (язык «ru» и тема «новости») — женщина о выборах
  вполглаза 4.6с (решение 2.0с): нейтрально (язык «ru», но не тема «новости») — два кота в саду
  листаю 0.0с (решение 1.9с):    мимо (не язык «en» и не тема «новости») — cat sleeps on a chair
```

Первое число — сколько ролик провисит на экране, в скобках — сколько думала
модель. Решение принимается синхронно, но параллельно с «взглядом», поэтому
из времени просмотра оно не вычитается лишний раз.

Строки печатаются **сразу**, по ходу прогона (`runlog.Log`), а не пачкой в
конце: сессия идёт несколько минут, и всё это время экран не должен молчать.
То же и у публикации. Выключается флагом `LIVE_LOG` в `config.py` — тогда
отчёт печатается целиком в конце, как раньше.

**Модель смотрит не только на картинку.** Вместе с кадром ей уходит подпись
под роликом — описание автора, его ник и название музыки, снятые из дерева
интерфейса. В промпте прямо сказано, что картинка и подпись одинаково важны:
картинка показывает, что происходит, подпись — о чём это и зачем снято.
Подпись уходит в модель как есть и учитывается наравне с картинкой.

**По умолчанию это выключено** (`READ_CAPTION = False`), и не зря. Замер на
живой ленте: `uiautomator dump` стоит там **12,7 секунды и не срабатывает ни
разу** — он ждёт, пока интерфейс замрёт, а видео играет всегда. Это было
12,7 из 16,7 секунд на ролик. Без него — 4,9 секунды: съёмка кадра по сети
2,7 + модель 2,1.

Текст с экрана модель и так читает сама — он попадает в поле «текст», и
запасной поиск слов идёт по нему. Так что включать `READ_CAPTION` имеет смысл только
для лент со статичной картинкой; тогда число попыток за сессию задаёт
`CAPTION_ATTEMPTS`, каждая стоит около 12 секунд.

Настроек ровно две — **одна тема и один язык**, лежат в `interests.json`.
Перезапускать ничего не надо, файл читается в начале каждой сессии.

```json
"тема": "новости",
"язык": "ru"
```

Тема пишется **своими словами**, а не выбирается из списка: «новости»,
«коты», «мемы про политику». Списков интересных и скучных категорий больше
нет — они противоречили друг другу (тема «новости» в интересном и категория
«новости» в скучном одновременно), и агент лайкал животных при выбранной
политике.

```
python main.py interests                        # показать настройки
python main.py interests --pick                 # спросить в диалоге (2 вопроса)
python main.py interests --edit                 # открыть файл для правки
python main.py interests --topic новости --lang ru
python main.py interests --lang -               # язык не проверять
python main.py interests --topic -              # смотреть всё подряд
```

Тему сверяет по смыслу текстовая модель: она получает описание ролика и
отвечает «да» или «нет». Если LM Studio недоступен, в ход идёт запасной
путь — поиск слов темы и её развёрнутого набора синонимов
(`topics_cache.json`) в описании, с поправкой на склонения.

### Три ступени

| совпало | вердикт | что делает | лайк |
|---|---|---|---|
| и язык, и тема | `интересно` | `human.dwell()`, но не меньше нейтрального — 7-20 с | да, с вероятностью `лайк` |
| только **тема** | `нейтрально` | `секунд_на_тему_без_языка` — 5-7 с | никогда |
| только **язык** | `нейтрально` | `секунд_на_язык_без_темы` — 4-6 с | никогда |
| ничего | `мимо` | листает сразу | никогда |

Нейтральное делится надвое не случайно: ролик по нужной теме, но на чужом
языке — это контент по делу, просто озвучен не так, и ему дают больше. А свой
язык на посторонней теме — просто фон.

### Два вида залипания, каждое раз в ~30 роликов

Все ступени выше дают отрезки одного порядка — 2, 5, 20 секунд. Живой человек
время от времени выпадает из этого ритма, и делает это двумя разными
способами:

1. **Досматривает один ролик целиком** — `config.DEEP_WATCH_EVERY = (25, 35)`.
2. **Откладывает телефон** — выходит из приложения и через несколько секунд
   возвращается: `config.LEAVE_APP_EVERY = (25, 35)`.

Оба считаются ИНТЕРВАЛОМ в роликах, а не шансом на каждом. Шанс давал
кучность: то три раза подряд, то ни разу за сессию. Интервал держит частоту,
а момент внутри границ остаётся случайным — постоянный шаг вроде «ровно
каждый тридцатый» виден в журнале с одного взгляда.

Короткое «отвлёкся на 10-40 секунд» — третье и отдельное: оно разыгрывается
шансом (`DISTRACT_PROBABILITY`) с выдержкой в семь минут.

Конец ролика ловится тем же способом, что и обычно, — по возврату картинки к
начальной (`_watch_video`), поэтому «целиком» означает именно один полный
просмотр, а не «полторы минуты на восьмисекундном ролике». Предел
`DEEP_WATCH_MAX_SEC = 90` нужен только для длинных. Если кадры из потока
недоступны, конец ловить нечем — тогда действует скромный
`DEEP_WATCH_NO_STREAM_SEC = 25`.

### Ещё три вещи, которые выдавали автоматику

Все три не про отдельное число, а про **закономерность**, которая видна
только на длинном ряду.

**Лайк больше не лежит в одной точке.** Раньше он ставился после того, как
просмотр закончился, и за 0.5–1.5 с до свайпа — то есть каждый лайк был на
одном и том же расстоянии от конца ролика. Теперь момент разыгрывается
(`human.like_moment`) и лайк ставит сам `_watch_video` посреди просмотра.
Распределение из двух частей, потому что и решений два: обычно «нравится»
приходит, посмотрев (поздняя часть), но бывает и мгновенное узнавание —
свой автор, знакомый звук. Одной бетой это не описывалось: ранних лайков
оставалось 4% вместо заметной доли. Если ролик оборвался на повторе раньше
задуманного момента, лайк всё равно ставится в конце — иначе их доля молча
уехала бы вниз на коротких роликах.

**Понравившийся ролик изредка смотрится по второму кругу.**
`REWATCH_PROBABILITY = 0.15`, только для вердикта `интересно`. Просмотр
обрывался на первом повторе ВСЕГДА, без единого исключения — то есть агент
не пересматривал ничего и никогда, а безусловные правила как раз и заметны.
Длина ролика к этому моменту уже известна (круг замкнулся), поэтому второй
круг отмеряется точно.

**Внимание дрейфует.** `state["mood"]` — множитель, медленно блуждающий
вокруг единицы (`human.drift`); он тянет за собой время просмотра и терпение
на неподходящем. Раньше каждый ролик брал числа заново и независимо от
предыдущих: правдоподобные поодиночке, они не складывались в правдоподобную
последовательность.

Замер: связь соседних роликов (автокорреляция по лагу 1) была **0.00** —
ровно то, чего у человека не бывает, — стала **+0.11**. Первая версия качала
настроение на ±20% и дала всего +0.02: собственный разброс `dwell()`
(логнормальный, σ=0.85) настолько велик, что настроения за ним не было
видно. Поэтому блуждание мультипликативное и с большим размахом.

Возврат идёт не к единице, а чуть ниже: у мультипликативного множителя
среднее равно exp(v/2) и всегда больше единицы, так что без поправки все
просмотры удлинились бы процентов на восемь. Дрейф должен менять порядок
значений, а не общий уровень — проверено, среднее 1.00.

### Заход в комментарии

Единственное место, где агент тапает **не** по лайку. До этого сессия
состояла из свайпов и двойных тапов и больше ни из чего — само по себе
заметно: живой человек в ленте что-нибудь да открывает.

`COMMENTS_PROBABILITY = 0.06`, не чаще раза в `COMMENTS_EVERY_SEC = 240`
секунд и только на том, что зашло: читать обсуждение под неинтересным
роликом человек не идёт.

**Как обходится главное препятствие.** Пока играет видео, `uiautomator` не
снимает дерево — интерфейс никогда не приходит в покой. Кнопку комментариев
пришлось бы искать по координатам, то есть гадать. Поэтому сначала
одиночный тап ставит ролик на паузу (точка та же, что у лайка, зона уже
выверена), экран становится статичным, дерево снимается — и кнопка
находится обычным селектором, как всё остальное в проекте.

Дальше каждый шаг подтверждается, а любая неудача откатывается:

| что пошло не так | что делает агент |
|---|---|
| тап не остановил ролик | ничего не открывает, листает дальше |
| кнопки нет в дереве | возвращает ролик в проигрывание |
| открылось не то (профиль) | «назад», `_ensure_feed`, возвращает ролик |
| кадр не сменился | не тапает вовсе — под пальцем может быть окно |

**Работает только в TikTok** — проверено живьём. У YouTube Shorts в дереве
выставлен только слой доступности (пауза и «следующее видео»), у Instagram
Reels — одни контейнеры: правой колонки кнопок нет ни там, ни там, и найти
кнопку селектором нечем. У обоих `comment_selectors` пусты, агент даже не
пытается.

Две вещи, которые пришлось выяснить на живом экране:

* **тапать по кнопке надо по играющему ролику.** С паузы не открывается —
  первый тап TikTok тратит на возобновление. Пауза нужна только затем, чтобы
  снялось дерево и стало известно, ГДЕ кнопка;
* **проверять открытие деревом нельзя** — при открытых комментариях видео
  играет сверху, и дамп по-прежнему пустой. Признак — вес кадра: панель
  роняет его втрое (замер 2248→903, 1999→599, 2307→861 КБ).

Проверить селекторы на своём телефоне:

```
python main.py comments-probe tiktok
```

Команда повторяет те же шаги, но ничего не нажимает — только показывает,
нашлась ли кнопка, и печатает дерево, если нет.

### Ссылки на понравившееся

Когда агент лайкает ролик, у которого лайков не меньше `LINK_MIN_LIKES`
(по умолчанию 50 000), он забирает адрес ролика и кладёт его в базу.

```
python main.py links                      # что накопилось
python main.py links --export ссылки.csv  # выгрузить таблицей
```

Хранится адрес, число лайков, автор, описание, лента и время. Порог не
украшательство: заход стоит семи тапов и перехода в «Интересное» и обратно,
то есть секунд десяти на каждом лайке, — и это лишние следы там, где вся
остальная сессия состоит из свайпов.

**Почему так сложно.** Число лайков лежит в дереве целиком — у кнопки
`content-desc` вида «Поставить лайк. Число лайков: 230500» (на экране то же
число сокращено до «230.5K», поэтому берётся именно `desc`). А вот адреса
ролика в дереве нет вовсе, его отдаёт только пункт «Ссылка» в листе
«поделиться» — и отдаёт в буфер обмена.

**Буфер обмена с компьютера не читается.** С Android 10 его видит только
приложение на переднем плане; `adb shell cmd clipboard` на этом телефоне не
реализован вовсе («No shell command implementation»), рута нет, а ADBKeyboard
умеет только вводить текст. Поэтому скопированное **вставляется в поле поиска
самого TikTok** и читается уже из дерева: экран поиска статичен, видео на нём
не играет, дерево снимается. Поле поиска, а не комментария — там рядом нет
кнопки «отправить», промахнуться в чужую ленту нечем. После чтения поле
вычищается забоем, чтобы адрес не всплыл хозяину телефона.

Кнопки поиска в самой ленте в дереве нет, поэтому путь идёт через нижнюю
вкладку «Интересное», а обратно — через «Главную». Заход стоит в конце
просмотра, перед свайпом: если лента после возврата покажет другой ролик,
терять уже нечего.

Порядок тот же, что и у комментариев, и по той же причине: кнопки ищутся
**на паузе** (пока играет видео, дерево не снимается), а тап делается по
**играющему** ролику — с паузы первый тап уходит на возобновление.

| что пошло не так | что делает агент |
|---|---|
| тап не остановил ролик | ничего не открывает, листает дальше |
| число лайков не прочиталось | не рискует, возвращает ролик |
| лайков меньше порога | разворачивается сразу, до листа «поделиться» |
| лист не открылся | «назад», `_ensure_feed`, возвращает ролик |
| в поле поиска не оказалось адреса | всё равно возвращается в ленту |

Проверить селекторы на своём телефоне:

```
python main.py link-probe tiktok
```

#### Shorts и Reels: то же самое, но вслепую

У YouTube и Instagram правой колонки кнопок в дереве нет вовсе — ни счётчика
лайков, ни «поделиться» (проверено живьём: 75 узлов у Shorts, 56 у Reels, и
все не о том). Поэтому там другой путь:

| что нужно | в TikTok | в Shorts и Reels |
|---|---|---|
| число лайков | `desc` кнопки в дереве | читает **зрение** с кадра |
| «поделиться» | узел, тап со случайным разбросом | **точка** из `recipes.json` |
| дорога до поиска | вкладка «Интересное» из дерева | Shorts — точки, Reels — вкладки из дерева |
| пункт «Ссылка» | селектор в листе | селектор в листе (лист снимается у всех) |

Зрению отдаётся один кадр на **лайкнутый** ролик — примерно каждый
четырнадцатый, — и ответ проходит тот же разбор, что подпись кнопки: не
число, «нет» или бессмыслица — ссылку не берём. Выключается
`LINK_LIKES_BY_VISION` в `config.py`.

Слепой тап опасен тем, что промах ничем не отличается от попадания, поэтому
проверяется каждый шаг: не открылся лист — «назад» и в ленту, не нашлась
строка поиска — возврат без записи. Ролик в любом случае остаётся
нетронутым.

Точки заданы **долями экрана**, а не пикселями, и требуют калибровки на своём
телефоне:

```
python main.py link-probe shorts     # и reels
```

Команда снимает экран, ставит крестики на все заданные точки и открывает
разметку в браузере (`frames/probe-shorts.html`). Крестик должен стоять на
кнопке; если нет — поправить доли в `recipes.json → _feed_apps → shorts`
(первое число — доля ширины, второе — доля высоты) и запустить снова. Заодно
команда показывает, что зрение прочитало вместо числа лайков.

Одна оговорка про повторы: TikTok отдаёт **короткую** ссылку вида
`tiktok.com/t/ZTDfNosFW`, и на один и тот же ролик она каждый раз разная —
проверено, две записи одного ролика получили разные адреса. Защита от
дублей по `url` в базе есть, но на такие повторы она не сработает.

### Время суток

`human.daypart()` — постоянный на всю сессию множитель: 0.78 к позднему
утру, 1.22 вечером. Вечером дольше смотрится и чаще случается залипание,
утром лента листается на бегу. Кривая гладкая (один косинус за сутки), а не
ступеньками по часам: скачок на границе часа — ровно тот резкий признак, от
которого избавляется весь модуль. В среднем по суткам ровно единица, так что
общий уровень не поехал.

Это про время, а не про настроение: за колебания внутри сессии отвечает
`drift`, они умножаются друг на друга.

**`DEEP_WATCH_ON_SKIPPED = False`** — залипать ли на том, что вкусы велели
пролистать. По умолчанию нет, и это осознанно: время просмотра — самый сильный
сигнал для рекомендаций, сильнее лайка, и досмотреть неподходящее до конца
значит попросить ленту показывать больше такого же. Программа уже приняла это
решение для лайков (`like_probability("скучно") == 0`), здесь то же самое,
только цена выше. Если ролик пролистывается, счётчик **не** перевзводится —
залипание случится на ближайшем подходящем, иначе на строгих вкусах оно не
сработало бы ни разу.

У интересного есть **нижняя граница**, и это не украшательство: `human.dwell()`
берётся из распределения с минимумом 1.5 с, и подходящий ролик регулярно
получал меньше неподходящего — ступени переворачивались. Порог равен верхней
границе нейтрального.

В логе сессии стоит время **на экране**, а в скобках — сколько думала модель:

```
  вполглаза 5.6с (решение 2.2с): нейтрально (тема «кулинария», но не язык «ru») — ...
```

Считаются только **заданные** условия. Пустая тема = смотреть всё на нужном
языке; пустой язык = не проверять его. Если задано лишь одно условие, средней
ступени не бывает вовсе: «совпало одно» и «совпало всё» — это одно и то же.

**Почему секунды, а не доля ролика.** Длину ролика агент не знает: TikTok её
не отдаёт, а дерево интерфейса в играющей ленте не снимается (см. ниже).
Сначала нейтральное считалось долей от обычного просмотра, но тот сам
случайный — выходило то 1,5, то 4 секунды, предсказать нельзя. Поэтому обе
нейтральные ступени заданы прямыми секундами.

Язык, который модель не назвала, чужим не считается — иначе под нож уходили
бы ролики без речи.

Вердикт пишется в базу вместе с версией правил (`jobs.RULES`), потому что
имена ступеней переживают смену логики: в старой схеме со списками категорий
«интересно» и «нейтрально» значили другое. Отчёт `stats` считает только
кадры нынешних правил и отдельно говорит, сколько отбросил.

Выключается флагом `VISION_DECIDE` в `config.py` — тогда лента листается как
раньше, а кадры просто разбираются для статистики.

**3. Спасение.** Когда селекторы не сработали и дерево не помогло, модель
смотрит на скриншот и говорит, что это за экран и что бы она нажала.
По умолчанию это **только запись в лог**: в сессии агент откатывается назад,
в маршруте публикации — падает с понятной ошибкой и кладёт рядом
`NN_vision.txt`.

### Настройки в `config.py`

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `VISION_ENABLED` | `True` | зрение вообще включено |
| `VISION_PROVIDER` | `local` | кто отвечает: `local` (свой сервер) или `api` (сервис в интернете) |
| `VISION_URL` | `http://127.0.0.1:1234/v1` | адрес сервера LM Studio |
| `VISION_MODEL` | `""` | пусто = найти визуальную модель самому |
| `VISION_CAPTURE` | `True` | снимать кадры в сессии |
| `VISION_DECIDE` | `True` | решать по теме: смотреть ролик или листать |
| `VISION_REALTIME` | `True` | разбирать в ленте фоновым потоком (когда решения выключены) |
| `VISION_MAY_TAP` | `False` | разрешить тапать по подсказке модели |
| `VISION_SHRINK` | `3` | во сколько раз ужимать кадр перед отправкой |
| `ESCAPE_ENABLED` | `True` | выбираться с незнакомого экрана своим умом |
| `ESCAPE_MAX_STEPS` | `5` | сколько действий даём на одну помеху |
| `ESCAPE_MAX_SECONDS` | `75` | потолок по времени на ту же помеху |

`VISION_MAY_TAP` действует **только в живой сессии**. В маршруте публикации
тапы по подсказке модели запрещены всегда: цена ошибки — опубликованное не туда
видео, а промахнуться по кнопке модель может всегда.

`ESCAPE_ENABLED` отдельного разрешения на тап не требует, и это не
недосмотр: там модель выбирает элемент из дерева, а не координату, поэтому
мимо кнопки не попадёт. Что именно ей показывают и чего не показывают —
в разделе «Выход из тупика».

### Что нужно со стороны LM Studio

1. Загрузить визуальную модель (`*-VL`, `gemma-3`, `minicpm-v`).
2. Developer → **Start Server** (порт 1234).
3. Проверить: `python main.py vision` — снимет текущий экран и покажет, что
   модель на нём увидела, с замером времени.

Модель ищется среди загруженных автоматически, поэтому менять её можно прямо
в LM Studio, не трогая конфиг.

### Что нужно со стороны сервиса по API

1. Взять ключ у выбранного сервиса (для Qwen это `DASHSCOPE_API_KEY` из
   личного кабинета Alibaba Cloud Model Studio).
2. Вкладка «Настройки» → «Где считать» → **По API**, выбрать сервис из списка
   (или вписать свой адрес), вписать ключ, сохранить. Из консоли то же самое:
   `python main.py vision --where api --url https://…/v1 --key sk-…`.
   Адрес можно копировать как есть — хвост `/chat/completions`, пропущенную
   схему и лишнюю косую черту программа уберёт сама.
3. Проверить: `python main.py vision` — снимет экран и покажет, что модель
   на нём увидела. Без телефона проверит хотя бы ключ и связь.

Ключ ложится в `settings.json` рядом с программой. **Этот файл намеренно не
попадает в комплект exe** (`build_exe.BESIDE`): комплект уезжает к другому
человеку, ключ — нет. Запасной путь — переменная `DASHSCOPE_API_KEY`.

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `API_URL` | `…dashscope-intl…/compatible-mode/v1` | адрес сервиса (пресет Qwen) |
| `API_MODEL` | `qwen-vl-plus` | имя модели |
| `API_TIMEOUT` | `60` | ждать ответа, секунд |
| `API_RETRIES` | `2` | сколько раз повторить 429 и 5xx |
| `API_JPEG` | `True` | перекодировать кадр в JPEG перед отправкой |
| `API_JPEG_QUALITY` | `4` | шкала `ffmpeg -q:v`: 2 лучше, 31 хуже |
| `VISION_FALLBACK` | `True` | сервис молчит — доработать на своём сервере |

**Кадр уходит в JPEG, и это не мелочь.** Ужатый PNG весит 931 КБ, в base64 —
1,2 МБ на КАЖДЫЙ ролик; тот же кадр в JPEG — 96 КБ. Перекодировка стоит
0,07 с (замер, 6 прогонов) и делается через ffmpeg — тот же, что нужен потоку
кадров. Без ffmpeg уходит PNG, в журнал печатается предупреждение.

**Чего в облаке не бывает.** Нечего разогревать (`warm_up` там оплачивает
рукопожатие TLS — первое соединение стоило 2,8 с — и заодно проверяет ключ)
и нечего перезагружать: `reload_model` возвращает `False`, а сессия на трёх
медленных решениях подряд пишет «перезагрузить нечего» вместо бесполезной
попытки.

**Неверный ключ и несуществующая модель не подменяются локальной моделью.**
`VisionError.fatal` отделяет поломку настроек от обрыва связи: связь —
повторяем и при неудаче уходим в LM Studio, настройки — говорим человеку.
Иначе агент молча работал бы «не на том», а чинить было бы нечего.

**Рассуждение выключено явно** (`enable_thinking: false`). Модели Qwen с
рассуждением включают его сами, а тогда ответ приходит только потоком и
обычный запрос падает. Нам оно и не нужно: пока модель думает, неинтересный
ролик висит на экране, а ответ здесь — одна строка JSON.

### Выход из тупика: модель убирает помеху сама

Раньше на незнакомом экране («Подпишитесь на друзей», запрос прав, лист
«поделиться») агент шёл по жёсткой лесенке: известная кнопка → «назад» →
перезапуск приложения. Перезапуск стоит полминуты и теряет место в ленте, а
окно чаще всего закрывается одним крестиком, который надо просто найти.

Теперь между «известной кнопкой» и «назад» стоит `escape.py`: модель смотрит
на экран, выбирает кнопку из списка, видит, что получилось, и пробует
дальше — до пяти шагов (`ESCAPE_MAX_STEPS`) или 75 секунд.

```
python main.py escape                    убрать то, что сейчас на экране
python main.py escape --app shorts       то же для другой ленты
python main.py escape --steps 8          дать больше попыток
```

**Модель жмёт не координаты, а элемент дерева.** Просить у 3B пиксели
бесполезно — половина ответов приходила мимо экрана. Список кнопок она
выбирает номером, и промахнуться мимо кнопки нельзя в принципе. Дерево на
таких экранах снимается: помеха статична, это не лента с играющим видео.

**Живая лента сюда не попадает.** Первым делом смотрим, снялось ли дерево.
Не снялось — значит перед нами лента, тревога ложная, и выход уходит, не
нажав ничего. Тот же признак, на котором стоит `_ensure_feed`.

**Не в том приложении — модель не спрашивают.** Найдено первым же живым
прогоном: «назад» вывалил агента на рабочий стол MIUI, и он честно выбирал
кнопки лаунчера («Экран 1», «Галерея») до конца лимита. Теперь пакет
проверяется перед каждым шагом, и приложение просто открывается заново.

**Опасные кнопки модели не показывают.** Права, оплата, вход в аккаунт,
подписки на людей, публикация, жалобы — такие подписи не попадают в список
(`NEVER`). А экран, с которого можно ОТПРАВИТЬ видео, распознаётся целиком
(`SENDING_MARKS`): на листе «поделиться» в список кнопок лезли имена
аккаунтов, «SMS», «Жалоба», «Неинтересно» — по подписи их не отличить от
безобидных. На таком экране остаются только закрывающие кнопки и значки без
подписи; выбирает по-прежнему модель, но испортить нечего.

**Два коротких вопроса вместо одного длинного** — это замер, а не вкусовщина.
Гонка формулировок на сохранённом экране профиля, 5 попыток на вариант,
верный ответ — кнопка «Главная»:

| Промпт | Верно | Время |
|---|---|---|
| длинный: правила, надписи экрана, поле «почему» | 0/5 | 1,1 с |
| надписи экрана + список кнопок | 2/5 | 0,4 с |
| «ты нажимаешь кнопки вместо человека» | 0/5 | 0,4 с |
| **только список кнопок и один вопрос** | **5/5** | **0,3 с** |

3B на длинном промпте не рассуждает, а переписывает его куски: сначала
выдавала дословно «Смахнуть подсказку-туториал» из примера правил, потом —
«Надписи на экране: …» из условия. Та же болячка, от которой в
`describe_frame` стоит `_same_as_example`. Поэтому спрашиваем по одному:
сначала «какую кнопку нажать», и только если кнопки не подошли — «что тогда
делать». Второй вопрос достаётся меньшинству экранов.

**Проверено живьём** (TikTok, 2026-08-29): профиль → лента за один шаг,
11 с; «Входящие» → лента за один шаг, 12 с; лист «поделиться» закрыт
крестиком без подписи за один шаг, 12 с; рабочий стол → приложение
возвращено за 11 с. Отладка без телефона:
`python scratchpad\escape_probe.py --save имя` снимает экран в файл, а
`--ask имя -n 5` гоняет по нему модель сколько угодно раз.

## Настройка маршрутов

**`recipes.json` — единственный файл, который придётся править**, когда
соцсеть обновит интерфейс. Код трогать не нужно.

### Как видео попадает в приложение

Единого способа нет — у каждой сети свой, и все три выяснены живьём:

| сеть | как открывается | почему так |
|---|---|---|
| TikTok | Intent `SEND`, адрес `content://` | работает как есть |
| YouTube Shorts | Intent `SEND`, адрес **`file://`** | по `content://` YouTube не открывается вообще |
| Instagram Reels | **через интерфейс** (`open_uri`) | Intent'ом видео не принимает никак |

Instagram проверен во всех вариантах: `content://`, `file://`, явная
`ShareHandlerActivity`, пункт «Reels» в окне выбора MIUI — везде открывается
главная лента, будто ничего не прислали. Поэтому туда агент заходит как
человек: лента Reels → камера → галерея → свежее видео → «Далее» → подпись →
«Поделиться». Видео к этому моменту уже залито и лежит в галерее первым.

Ещё одна деталь: `MEDIA_SCANNER_SCAN_FILE` на Android 12 не делает ничего,
файла не было в медиатеке вовсе. Рабочий способ — `content call --uri
content://media --method scan_file`, он и сканирует, и возвращает адрес.

**«Картинка в картинке» ест нажатия.** После сессии в Shorts YouTube остаётся
плавающим окошком поверх экрана и перехватывает тапы по кнопкам — в логе это
выглядит как «нажал, но экран не сменился». Перед публикацией соседние
видеоприложения прибиваются (`device.close_overlays`).

Селекторы в `recipes.json` — это стартовые догадки. Уточни их под свою версию
приложения: открой нужный экран на телефоне и выполни

```
python main.py dump
```

Скрипт напечатает настоящие тексты, id и координаты всех элементов. Впиши
найденные `resource-id` в маршрут — они устойчивее текста, потому что не
зависят от языка интерфейса.

Если шаг не нашёл элемент, агент сохранит в `logs/` скриншот и полный текст
дерева — по ним видно, что именно поменялось.

### Почему после ввода описания стоит `hide_keyboard`, а не `back`

Клавиатуру после ввода надо убрать, иначе она закрывает кнопку публикации.
Но голое «назад» при уже спрятанной клавиатуре — это обычная навигация: в
TikTok оно уводило с экрана описания обратно в редактор, и финальная кнопка
не находилась. ADBKeyboard свою панель почти не рисует, так что прятать чаще
всего нечего. `hide_keyboard` жмёт «назад», только если клавиатура правда на
экране (системный флаг `mInputShown`; поле `mIsInputViewShown` у самой IME
для этого не годится — оно остаётся `true` и там, где полей ввода нет).

## Порядок первого запуска

1. `python main.py doctor` — телефон виден, дерево читается
2. `python main.py unlock` — разблокировка работает
3. Открой TikTok вручную, `python main.py dump` — уточни селекторы
4. `python main.py post video.mp4 -c "тест"` — **в сухом прогоне**
5. Посмотри скриншоты в `logs/`, убедись, что агент дошёл до нужной кнопки
6. Только потом `DRY_RUN = False` в `config.py`

## Предохранители

- **`DRY_RUN = True`** по умолчанию: агент делает всё, кроме финального
  нажатия «Опубликовать». Первую неделю гоняй так.
- **Стоп-кран:** `python main.py stop` или команда `/stop` боту.
  Проверяется перед каждым действием и внутри циклов.
- **Лимиты:** `MAX_POSTS_PER_DAY`, `MAX_SESSIONS_PER_DAY` — баг в цикле
  не превратится в сто постов за ночь.
- **Логи:** скриншот и разбор каждого шага в `logs/<дата>_<сеть>/`.

## Telegram-бот

Токен вставляется на вкладке **Бот** в окне приложения и ложится в
`telegram.json` рядом с программой (в архив для передачи он не попадает).
Владельца бот запоминает сам — по первому написавшему; чужие игнорируются.

Кидаешь боту видео с подписью — оно уходит в публикацию. Два правила:

- **Сети не названы в подписи — публикует во все.** Назвать можно как
  угодно: «tiktok», «#шортс», «в инсту». Падежи понимает (алиасы — основы
  слов плюс до трёх букв хвоста), служебные слова из описания вырезает.
- **Время не названо и `POST_TIMES` пуст — публикует сразу.** Написал
  «в 18:30» — поставит на это время (прошедшее считается завтрашним).
  В `POST_TIMES` есть часы — дождётся ближайшего.

Команды: `/status`, `/stop`, `/start`, `/links`.

Публикация из бота встаёт в ту же очередь на одно действие, что и кнопки в
окне: телефон один, и пост не должен начаться посреди сессии.

Бота можно держать включённым отдельно от службы — телефон ему не нужен,
если дело только в ссылках:

```
python main.py bot        только приёмник, ничего не публикует по расписанию
python main.py serve      служба целиком: расписание, сессии и бот вместе
```

### Ссылки: кидаешь в чат — сохраняется

Кроме видео бот принимает **ссылки, и из любой соцсети**. Присланное не
публикуется — оно ложится в ту же подборку, что и лайкнутое агентом в ленте,
и приходит обратно по `/links`.

```
https://vm.tiktok.com/ZMxxxx/            одна ссылка
глянь это в ролик https://youtu.be/... и vk.com/video-1_2    несколько + заметка
```

- **Сеть определяется по домену** (`weblink.py`): TikTok, YouTube, Instagram,
  VK, X, Telegram, OK, Pinterest, Reddit, Rutube, Дзен, Facebook, Threads,
  Snapchat, Twitch, Likee, Kwai, Bilibili, Coub, Vimeo, Yappy. Домен
  незнакомый — ссылка всё равно сохраняется, просто без имени сети: адрес
  нужен сам по себе.
- **Приписка становится заметкой** и видна в подборке рядом со ссылкой.
- **Адрес причёсывается перед записью**: снимаются метки того, кто и откуда
  скопировал (`utm_*`, `igshid`, `is_from_webapp`, `si`), хвостовой слэш и
  якорь. Полезное при этом выживает — `v` и `t` у YouTube это ролик и
  секунда, а вот `t` у X, наоборот, метка, поэтому список чистки у части
  сетей свой.
- **Чистка живёт в `jobs.add_link`, а не у бота.** Иначе одна и та же
  ссылка с телефона («…/ZTDfNosFW/») и из чата («…/ZTDfNosFW») ложилась бы
  двумя строками мимо UNIQUE — поймано на первом же прогоне.
- **Ссылка в подписи к видео не считается**: сообщение с файлом — это
  публикация, даже если в тексте есть адрес.
- Из одного сообщения берётся не больше 20 адресов: пересланный пост из
  канала легко несёт полсотни ссылок в разметке, и подборка превратилась бы
  в его копию. Спрятанные за текстом адреса (`text_link`) тоже находятся.

Руками, без Telegram, — то же самое:

```
python main.py links --add https://vm.tiktok.com/ZMxxxx/ "в ролик"
```

### Подборка понравившегося

Ссылки — и забранные агентом в ленте, и присланные в чат — бот присылает
списком, сам раз в день и по требованию:

```
/links          новое, чего ещё не присылал   (и помечает отправленным)
/links 20       последние 20, ничего не помечая
/links все      последние 50
```

У присланных в чат вместо числа лайков стоит «прислано в чат»: лайков мы
не знаем, а «♥ 0» читалось бы как «ноль лайков» — то есть ровно наоборот.

Каждая ссылка — отдельным абзацем: число лайков, автор, описание, адрес
последней строкой, чтобы по нему было удобно попасть пальцем. Развёртка
ссылок выключена — иначе десять адресов растянулись бы на весь экран.
Длинная подборка режется на сообщения **по целым ссылкам**: разрыв посреди
адреса превращает его в мусор.

Часы задаются в `config.py`:

```python
LINKS_DIGEST_TIMES = ["21:00"]   # пусто — только по команде
LINKS_DIGEST_MIN = 1             # меньше этого числа новых — подборка ждёт
```

Разброса у этих часов нет: подборка ничего не делает с телефоном, прятать её
ритм не от кого. По той же причине она **не пропускается задним числом** —
служба, поднятая в 21:05, отправит её сразу, а не завтра.

Отметка «уже отправлено» живёт в базе (`links.sent`), а не в файле рядом:
телефонов может быть несколько, у каждого свой процесс. Ставится она **после**
подтверждения от Telegram — оборванная связь оставляет ссылки в очереди, а не
съедает их молча.

Без токена приёмник просто выключен, работает папка `watch/`: бросаешь туда
видео (и рядом одноимённый `.txt` с описанием) — попадает в очередь.

Рабочая папка — `C:\Users\Admin\Desktop\PhoneAgent`.

## Что нужно знать

**Ограничения без нейросети.** Скрипт встанет, если приложение сильно
переделает экран публикации, и не разберётся на совсем незнакомом экране
(A/B-тест, новая фича). Чинится правкой `recipes.json` — обычно одна строка.
Универсальный закрыватель окон (`ui.dismiss_popup`) сам разбирается с
обновлениями, «оцените нас» и запросами разрешений.

**Правила площадок.** Автоматизация нарушает пользовательские соглашения
TikTok и Instagram. При двух-трёх постах в день со своего аккаунта и
человекоподобном поведении риск невелик, но не нулевой: аккаунт могут
ограничить, и апелляция обычно не работает. Не заводи на этот телефон
ничего, что жалко потерять.

**Разблокировка по расписанию** означает, что телефон периодически лежит
открытым. Держи его дома и не ставь на него банковские приложения.

## Файлы

```
config.py       все настройки
adb.py          вызовы ADB, переподключение
ui.py           дерево экрана, поиск элементов, закрытие окон
human.py        задержки, свайпы, разброс — ни одной константы
device.py       разблокировка, PIN, ввод текста, заливка файлов
recipes.json    маршруты публикации  ← правишь ты
poster.py       исполнитель маршрутов
session.py      живые сессии в ленте
escape.py       выход из незнакомого экрана: модель жмёт кнопки сама
weblink.py      ссылки из чата: какая соцсеть, чистка меток, повторы
mirror.py       трансляция экрана (scrcpy + запасной viewer)
jobs.py         очередь SQLite
telegram_bot.py приём видео и отчёты
scheduler.py    расписание дня со случайным разбросом
devices.py      пространство телефона: своя очередь, расписание, вкусы
fleet.py        несколько телефонов: по процессу на каждый, надзор за ними
gate.py         очередь к общему ресурсу между процессами (модель, бот)
main.py         команды
selftest.py     проверка логики без телефона
```

Проверки, которым телефон не нужен, гоняются пачкой:

```
python scratchpad\all_tests.py        один круг
python scratchpad\all_tests.py 8      восемь кругов подряд
```

Круги — не перестраховка: половина проекта построена на случайных величинах
(разброс расписания, свайпы, момент лайка), и проверка, прошедшая один раз,
могла просто попасть в удачный розыгрыш. Прогон печатает, сколько кругов из
скольких сошлось у каждой проверки. Тесты, которым нужен живой телефон
(`link_live`, `link_debug`, `adb_multi`, `fleet_*`), в пачку не входят.
